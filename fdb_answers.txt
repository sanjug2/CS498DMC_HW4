Q1: FDB decouples the components of TMS (transaction management) and SS (storage) so that each can scale independently and also recover independently. TMS will tackle transaction ordering, identifying conflicts and coordinating commits and the SS will store and get key-value data.
Q2: The resolver will identify read-write conflicts for concurrent transactions during the commit process. This is after the transaction will deliver the read and write conflict ranges but before the commit is approved.
Q3: The read version will find a consistent snapshot for the database the transaction reads. This will enable transactions to locate data from the same logical timestamp. Conflict detection and commit ordering will allow FDB to maintain serializability.
Q4: Snapshot reads are different from standard reads in that they don't automatically provide conflict ranges the way that standard reads do. Snapshot reads reduce unnecessary conflicts that way, while for standard reads a transaction might be rejected if a different one alters the data that was read. Snapshot reads should be used if the transaction doesn't need to protect those read values from concurrent modifications.
Q5: FDB recovery is "cheap" because storage and persistent logging are separated. LogServers keep a record of committed changes, while StorageServers apply those changes to the data. Since the changes are already safely persisted, the system doesn't need to replay the entire redo log before recovery. This decreases recovery time.
